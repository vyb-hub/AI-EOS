# Critical Corrections

## 1. AI-EOS is NOT associated with any company

AI-EOS is **not** any single company's Engineering Operating System.

It is an independent, vendor-neutral Engineering Operating System
designed to be reusable across:

-   individuals
-   startups
-   engineering teams
-   enterprises
-   open source projects

Products adopt AI-EOS.

Organizations do not own AI-EOS.

------------------------------------------------------------------------

## 2. AI-EOS is an Operating System, not documentation

Documentation is an output.

AI-EOS governs:

-   engineering philosophy
-   governance
-   architecture
-   decision making
-   reviews
-   documentation
-   release management
-   institutional memory
-   AI collaboration

Documentation is only one artifact produced by the operating system.

# New Architectural Principles

## Four Knowledge Domains

AI-EOS separates knowledge into four independent domains.

``` text
Founder Knowledge
Engineering Knowledge
Product Knowledge
Operational AI Knowledge
```

These evolve independently but remain connected.

------------------------------------------------------------------------

## Founder Knowledge Principle

AI must never invent:

-   vision
-   mission
-   values
-   project DNA
-   founder philosophy

AI should instead:

-   facilitate workshops
-   ask questions
-   expose inconsistencies
-   generate frameworks
-   document decisions

The founder owns founder knowledge.

------------------------------------------------------------------------

## Stable Core vs Capabilities vs Experiments

Everything inside AI-EOS belongs to one of three layers.

### Stable Core

-   Constitution
-   Governance
-   Engineering Philosophy
-   Standards

### Capabilities

-   Templates
-   AI Agents
-   Workflows
-   MCP integrations
-   Prompt libraries

### Experiments

-   Research
-   Prototype agents
-   New workflows
-   Emerging AI techniques

Only mature capabilities graduate into the Stable Core.

AI-EOS treats **Context Engineering** as a first-class discipline.

Context includes:

-   Engineering Charters
-   ADRs
-   Architecture history
-   Release history
-   Engineering journals
-   Knowledge indices
-   Repository structure
-   Project memory

High-quality context produces high-quality engineering.

-   Acceptance Criteria

-   Risks

-   Completion Evidence

# Documentation Evolution Strategy

As AI-EOS grows, it should evolve like a software product rather than a
single, ever-growing context document.

## Guiding Principle

Do not continuously replace one large context file.

Instead, version AI-EOS through modular documents with clear ownership.

Recommended structure:

-   **Constitution**: Stable, non-negotiable principles that rarely
    change.
-   **Engineering Philosophy**: How engineering decisions are made and
    the trade-offs we value.
-   **Architecture Decision Records (ADRs)**: Significant architectural
    and governance decisions with rationale.
-   **Engineering Charters**: The contract for each unit of work,
    including scope, constraints, acceptance criteria, and evidence of
    completion.
-   **Working Agreements**: Model- or tool-specific guidance for
    collaborators such as ChatGPT, Claude Code, Gemini, Codex, Cursor,
    or future AI systems.
-   **Standards & Templates**: Reusable engineering assets.
-   **Release Notes & Changelog**: Record of every meaningful evolution
    of AI-EOS.

## Evolution Model

Every significant change to AI-EOS should follow the same discipline it
expects from engineering projects:

``` text
Proposal
    ↓
Discussion
    ↓
Architecture Review
    ↓
Approval
    ↓
Implementation
    ↓
Documentation
    ↓
Release
    ↓
Changelog
```

This ensures AI-EOS remains stable at its core while continuously
evolving its capabilities.
